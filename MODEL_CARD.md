# DRISHTI model card

**Status:** finalist prototype · **Owner:** Team HawkEye · **Last updated:** 30 August 2026

## What the system predicts

DRISHTI uses two offline-trained, classical scikit-learn models for advisory case triage:

- **Detection model:** a `HistGradientBoostingClassifier` trained on closed cases to estimate whether an open case resembles historically detected cases. The UI converts this into an undetected-risk ranking.
- **Resolution-duration model:** a `HistGradientBoostingRegressor` trained where a reliable resolution date exists to estimate days to resolution and highlight possible stall risk.

Models are trained by `apps/api/scripts/train_models.py`, saved as dataset-scoped artifacts, and loaded for inference by the API. They are not trained inside a web request.

## Intended use

The output is a **decision-support signal for an authorized officer** deciding what to review next. It can help prioritize open cases, surface data-quality questions, and direct attention to unusual patterns. It must be read alongside case evidence, local context, legal procedure, and supervisory review.

It is not an arrest recommendation, guilt assessment, bail or sentencing tool, automated resource-allocation authority, or substitute for investigation. No adverse action should be based solely on a DRISHTI score.

## Data and features

The public finalist deployment uses seeded, synthetic demonstration data generated by the repository scripts. Planted patterns make workflows observable; they do not represent the prevalence, complexity, missingness, or institutional processes of operational Karnataka Police data.

Permitted inputs are case-level facts resolved through semantic roles: crime type, gravity, area, occurrence hour, day of week, reporting delay, property loss, and accused count when a reliable case relationship exists.

**Caste, religion, names, personal identity, and demographic identity attributes are prohibited model features.** This boundary is enforced in the feature-building code and covered by backend tests. Socio-demographic aggregates may appear in separate descriptive area analytics, but they are not inputs to the case-triage models.

## Reported prototype metrics

The deployed synthetic finalist seed reported the following snapshot during hardening on 27 August 2026:

| Signal | Seeded demo result | What it measures |
|---|---:|---|
| Detection ROC AUC | 0.7781 | Ranking quality on a random 25% holdout of labelled, closed synthetic cases |
| Area-risk capture@k | 54.3% | Share of incidents in the following seven days that fell in the top-risk areas, averaged over up to three retrospective weekly cutoffs |

These are **prototype diagnostics on synthetic data, not claims of real-world police effectiveness**. AUC uses a deterministic random split (`random_state=42`), not a temporal, district-held-out, or external validation cohort. Capture@k is a retrospective check against the dataset's own recent history; it is not a calibrated probability or causal impact estimate. Regenerating data, changing row counts, or retraining can change both results. The current artifact-specific values are recorded in each dataset's `models/meta.json` and insights response.

No production threshold, fairness target, or operational service level has been established. The duration MAE is intentionally not promoted here because it is seed- and artifact-specific and has not been externally validated.

## Explanations and the LLM boundary

DuckDB, NumPy, scikit-learn, NetworkX, and deterministic application code compute all counts, scores, backtests, rankings, graph links, and model factors. Case explanations use global permutation importance plus the case's value relative to the training baseline; they are directional aids, not causal explanations or SHAP values.

The LLM may select from allow-listed analytical tools and narrate returned results in English or Kannada. It does **not** calculate statistics, alter model outputs, write to the evidence store, or create predictive labels. When the LLM is unavailable, classical analytics and deterministic fallback summaries remain available.

## Known limitations and risks

- Synthetic patterns are cleaner than operational records and can inflate apparent learnability.
- A random holdout can place similar cases in both train and test sets; temporal and cross-district generalization remain unproven.
- Status labels reflect recorded workflow outcomes, not an objective measure of investigation quality.
- Historical labels can encode reporting, staffing, prioritization, and data-entry bias even when protected attributes are excluded.
- Missing or inconsistent semantic roles can remove features or make a model unavailable.
- Accused count can leak outcome information when records are added only after detection. The synthetic generator and model code explicitly flag this risk; feature importance must be inspected before trusting a run.
- Area and crime-type features can act as proxies for sensitive context. Excluding caste and religion is necessary but not sufficient for fairness.
- Predictions can become stale as crime patterns and investigative processes change.
- Kannada narration quality depends on the served language model and requires human review.

## Evaluation required before operational use

Before any pilot with real data, DRISHTI requires data-owner approval, privacy and legal review, a documented retention policy, and evaluation on a time-separated holdout. The evaluation should report calibration, sensitivity/specificity at proposed review thresholds, subgroup and district error analysis, missing-data robustness, feature leakage checks, drift monitoring, and comparison with a transparent non-ML baseline. Thresholds should be chosen with officers and affected governance stakeholders, then monitored after deployment.

Operators must be able to see data freshness, model version, confidence, contributing factors, and an audit trail; override decisions must remain with humans.

## Reproducing the prototype evaluation

Generate the deterministic seed datasets, then run:

```text
cd apps/api
python scripts/train_models.py
python scripts/smoke_insights.py
```

Set `PYTHONPATH=.` and `DATA_DIR=<repo>/data` first as shown in the root README. Inspect `<repo>/data/<dataset-id>/models/meta.json` for the baked model diagnostic and the insights API response for the current capture@k result.
